# 请求链路说明

本文档用于说明 Discourse 中一次典型请求如何从入口进入系统、经过业务处理、触发异步任务，并最终返回给前端或写入持久化存储。

## 1. 总体说明

Discourse 的请求链路建立在 Rails 应用模型之上，但由于项目本身具备插件体系、事件机制、后台任务和前端 SPA，因此实际链路比普通 Rails CRUD 应用更复杂。

一个完整请求通常会经历以下阶段：

1. 请求进入路由系统
2. 中间件和基础校验生效
3. controller 接收请求
4. 权限和参数校验
5. service / model 执行业务逻辑
6. 访问数据库、缓存或其他基础设施
7. serializer 组织响应
8. 必要时触发事件与异步任务
9. 前端消费结果并更新界面

## 2. 路由阶段

Discourse 的路由入口位于 `config/routes.rb`。路由负责将 URL 映射到对应 controller action。

路由系统中可看到多类入口：

- 站点页面
- 管理后台
- Webhook
- Sitemap
- 向导与安装流程
- 用户、群组、分类、设置相关接口
- 插件扩展出的路由

因此，路由阶段不仅是 URL 分发，也是整个系统能力边界的体现。

## 3. 中间件阶段

请求在进入 controller 前，会先经过 Rails 和应用自定义中间件。

Discourse 在启动阶段注入了多种中间件，例如：

- 默认响应头处理
- 主机名校验
- Content Security Policy 相关处理
- 爬虫钩子处理
- 异常处理
- 脚本 nonce 注入

这些中间件负责：

- 安全控制
- 请求预处理
- 统一响应头
- 错误兜底
- 页面脚本安全策略支持

## 4. Controller 阶段

Controller 是请求的第一层业务入口，常见职责包括：

- 解析参数
- 校验请求合法性
- 调用权限判断
- 调用 service、model 或 query 对象
- 返回 JSON、HTML 或重定向

Discourse 中 controller 数量较多，既包含面向普通用户的接口，也包含管理后台接口和系统接口。

## 5. 权限判断阶段

在 Discourse 中，权限并不只依赖 controller 的 before_action，而是大量通过 `Guardian` 体系来统一封装。

权限判断通常会考虑：

- 当前用户身份
- 群组与角色
- 站点设置
- 资源所属关系
- 插件扩展规则

这种设计可以减少权限逻辑散落的问题，也便于插件复用统一的授权模型。

## 6. 业务逻辑阶段

### 6.1 Model 参与

简单请求会直接通过 model 完成数据读取与写入，例如：

- 获取主题列表
- 查询用户资料
- 拉取标签或分类数据

### 6.2 Service 参与

复杂请求通常会引入 service 层进行流程编排，例如：

- 发帖
- 编辑内容
- 用户合并
- 通知派发
- 搜索索引更新
- 上传处理

service 的作用是把跨多个 model 的操作组织成一条清晰业务链路。

## 7. 数据访问阶段

### 7.1 PostgreSQL

PostgreSQL 是大多数请求的主数据源，主要负责：

- 读取业务实体
- 保存写操作结果
- 查询关联关系
- 记录日志和历史状态

### 7.2 Redis

Redis 常用于：

- 缓存热点数据
- 保存临时状态
- 支撑异步与消息相关能力
- 减轻数据库压力

### 7.3 外部依赖

部分请求还会访问外部依赖，例如：

- 对象存储
- 邮件服务
- 第三方登录服务
- Webhook 目标系统

## 8. 响应阶段

业务逻辑完成后，controller 通常会借助 serializer 输出结构化结果。

serializer 的作用包括：

- 控制字段暴露范围
- 根据当前用户作用域返回不同内容
- 统一 API 输出格式
- 提供前端渲染需要的聚合数据

对于 SPA 前端来说，serializer 是后端和前端之间的重要契约层。

## 9. 异步任务阶段

Discourse 中很多请求不会在主线程中完成全部工作，而是在返回响应前后，把一部分耗时动作放入后台任务。

常见异步场景包括：

- 邮件发送
- 通知推送
- 索引更新
- 图片处理
- 外部系统同步
- 清理和修复任务

这样做的好处是：

- 减少用户等待时间
- 提高 Web 请求吞吐量
- 将高成本操作移动到 Worker 进程

## 10. 事件触发阶段

除了 job 之外，Discourse 还广泛使用事件机制。

一个请求在完成核心业务后，可能触发事件，供插件或扩展逻辑监听，例如：

- 用户首次登录
- 用户加入群组
- 内容创建或更新
- 某些站点动作完成

事件机制让系统具备良好的可扩展性，插件可以在不侵入核心代码的情况下接入请求链路。

## 11. 典型请求示例

### 11.1 浏览页面

以浏览主题页面为例：

1. 浏览器请求某个主题 URL
2. 路由命中对应 controller
3. controller 读取 topic、post、category、user 等数据
4. 权限系统判断用户是否可见
5. serializer 组织页面所需结构
6. 前端渲染主题内容与附加状态

### 11.2 创建帖子

以发帖为例：

1. 前端提交帖子数据
2. controller 接收并校验参数
3. Guardian 判断当前用户是否有发帖权限
4. service 执行内容处理、格式化、风控、上传解析
5. model 写入 topic / post / 关联数据
6. 触发通知、搜索索引、统计等异步任务
7. 返回创建结果给前端

### 11.3 管理后台操作

以管理员更新站点设置为例：

1. 管理员提交设置修改请求
2. controller 校验管理员权限
3. setting validator 验证参数
4. 数据写入配置系统
5. 触发缓存刷新、依赖更新或后续事件
6. 返回更新后的结果

## 12. 插件对请求链路的影响

插件会影响请求链路的多个阶段：

- 注册新路由
- 在 controller 或 model 中追加行为
- 扩展 serializer 字段
- 监听事件
- 增加后台任务
- 影响权限判断

这意味着请求链路并不完全由核心代码控制，而是一个“核心 + 扩展点 + 插件”共同参与的运行时体系。

## 13. 请求链路总结

Discourse 的请求链路具有以下特点：

- 基于 Rails 标准请求模型
- 通过 Guardian 做统一权限控制
- 通过 service 层承接复杂业务流程
- 通过 serializer 控制输出结构
- 通过 Redis 与 Sidekiq 处理高频和异步工作
- 通过事件和插件体系支持深度扩展

因此，理解请求链路的关键，不只是理解 controller 到 model 的调用关系，更要理解权限、事件、异步任务和插件扩展点如何共同参与一次请求的执行。
