# 部署架构说明

本文档用于说明 Discourse 的运行环境、进程划分和部署时需要关注的关键组件。

## 1. 部署目标

Discourse 的部署架构主要服务于以下目标：

- 支持稳定的在线论坛服务
- 将 Web 请求、后台任务和定时任务分离
- 通过缓存与队列提升吞吐能力
- 支持对象存储、邮件服务和外部集成
- 兼容多站点与可配置化运行方式

由于 Discourse 是一个成熟的社区平台，它的部署思路不是“单进程跑全部”，而是围绕应用、后台 worker、调度器和基础设施服务进行协同。

## 2. 运行组件

### 2.1 Web 进程

Web 进程负责处理来自浏览器和外部系统的 HTTP 请求。

它的职责包括：

- 处理页面请求和 API 请求
- 执行 controller / service / model 逻辑
- 返回 HTML、JSON 或重定向响应
- 触发异步任务或事件

### 2.2 后台 Worker

后台 Worker 一般由 Sidekiq 承担，主要负责执行耗时任务，例如：

- 邮件发送
- 通知分发
- 搜索索引更新
- 图片处理
- 清理过期数据
- Webhook / 外部集成处理

将这些操作放入后台队列可以避免阻塞主请求线程。

### 2.3 定时调度器

Discourse 通过调度机制执行定期任务，例如：

- 清理任务
- 统计任务
- 过期数据回收
- 索引维护
- 备份与修复流程

调度器确保系统能够自动完成周期性维护工作。

### 2.4 数据库

PostgreSQL 是 Discourse 的主数据存储，承载：

- 用户与权限数据
- 帖子与主题
- 分类与标签
- 通知与审核
- 站点设置与插件数据

由于社区系统的数据关系复杂，PostgreSQL 作为主数据库是非常合适的选择。

### 2.5 Redis

Redis 在 Discourse 中承担多个角色：

- 缓存
- 临时状态保存
- 队列相关数据
- 运行时共享状态
- 消息与推送相关辅助能力

Redis 是性能和响应速度的重要保障。

### 2.6 对象存储

对象存储通常用于：

- 用户上传文件
- 图片与附件
- 备份文件
- 媒体资源

Discourse 支持本地存储与 S3 类存储方案，方便部署在不同环境中。

### 2.7 邮件服务

邮件系统是社区平台的重要外部依赖，用于：

- 注册与验证
- 通知提醒
- 订阅邮件
- 系统消息
- 备份与管理通知

因此部署时需要配置稳定的 SMTP 或邮件服务提供商。

## 3. 标准部署拓扑

一个典型的 Discourse 部署拓扑可以概括为：

- 反向代理 / 网关
- Web 应用进程
- Sidekiq Worker
- Scheduler
- PostgreSQL
- Redis
- 对象存储
- 外部邮件与第三方服务

这是一种非常典型的 Web + Queue + Database 架构。

## 4. 请求与任务分流

### 4.1 请求路径

用户访问页面时，请求一般流向 Web 进程：

1. 反向代理接收请求
2. 路由转发给 Rails Web 进程
3. Controller 处理请求
4. 数据库或缓存读取结果
5. Serializer 输出响应
6. 前端渲染或更新

### 4.2 异步路径

当业务需要执行耗时操作时：

1. Web 进程接收请求
2. 业务逻辑创建 job
3. job 进入 Sidekiq 队列
4. Worker 异步执行
5. 结果写回数据库或触发后续事件

### 4.3 定时路径

对于周期性任务：

1. Scheduler 按时间触发任务
2. 任务进入队列或直接执行
3. Worker 完成处理
4. 系统状态被更新

## 5. 配置与启动方式

Discourse 的配置主要集中在 `config/` 目录，并通过环境变量和站点配置进行调整。

### 5.1 核心配置来源

- `config/application.rb`
- `config/environments/*`
- `config/initializers/*`
- `config/database.yml`
- 站点设置与全局配置

### 5.2 启动时关注点

部署时需要确保以下能力可用：

- 数据库连接正常
- Redis 可访问
- 邮件服务可投递
- 对象存储权限正确
- 站点 URL 与 CDN 配置正确
- 插件与主题加载正常

## 6. 性能与扩展建议

### 6.1 常见优化点

- 将耗时逻辑放入后台任务
- 减少请求中直接做大规模查询
- 合理使用缓存
- 搜索与索引维护异步化
- 上传与图像处理放到专门流程中

### 6.2 横向扩展思路

Discourse 比较适合按以下方式扩展：

- 增加 Web 实例数
- 增加 Worker 实例数
- 将数据库与 Redis 独立部署
- 将对象存储外部化
- 按需拆分定时任务执行节点

## 7. 安全与可维护性

部署 Discourse 时，建议重点关注：

- HTTPS 与反向代理安全
- 邮件域名与 SPF / DKIM / DMARC
- Redis 与数据库访问控制
- 文件上传安全
- 插件和主题的版本兼容性
- 管理后台权限边界

## 8. 故障恢复与运维

Discourse 提供备份与恢复相关能力，因此部署时应建立完整运维策略：

- 定期备份数据库和对象存储
- 监控 worker 队列积压
- 监控邮件发送失败率
- 监控 Redis 和数据库连接情况
- 定期检查索引与清理任务

## 9. 部署架构总结

Discourse 的部署架构可以概括为：

- Web、Worker、Scheduler 角色分离
- PostgreSQL 作为核心数据源
- Redis 承担缓存与运行时辅助能力
- 对象存储承载上传与备份
- 邮件与第三方服务构成外部依赖

这种架构兼顾了稳定性、可扩展性和运维可控性，适合中大型社区长期运行。
